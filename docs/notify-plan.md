# Вывод произвольного текста на прибор («мониторчик как табло сообщений»)

> Черновик, обсуждается. Вопрос пользователя: может ли любое устройство в сети отправить на прибор
> текст, а прибор просто его показал. Сценарий: разные ПК и устройства умного дома иногда присылают
> короткие сообщения (10–200 знаков), прибор показывает их и возвращается к метрикам.

## Короткий ответ

Сложность средняя: **три независимых куска**, каждый делается за вечер, и почти всё нужное в прошивке
уже есть. Главный ограничитель — не софт, а железо: одна кнопка настройки и панель 200×200, где
длинный текст придётся показывать страницами.

## Что уже есть (не надо делать с нуля)

## Часть 1. Адрес в локальной сети

Сегодня прибор либо получает адрес от роутера через **мост Windows** (`docs/addressing.md`, вариант A,
`netinfo.h`: `NET_MODE_ROUTER`), либо уходит в аварийный режим `192.168.7.1` со своим DHCP
(`NET_MODE_EMERGENCY`). То есть локальный адрес у него **уже бывает** — но только пока включён ПК и
мост жив. Для «умного дома» это неправильная зависимость: лампе и датчику ПК не нужен.

Правильный путь — **вариант C из того же документа**: включить в прошивке Wi-Fi и подключать прибор
к домашней точке доступа как обычный клиент. Тогда:

* прибор получает адрес от роутера сам, без ПК и без моста;
* USB-кабель продолжает работать как сейчас (диск `INKMETRICS` + `192.168.7.1` для агента метрик):
  два сетевых интерфейса одновременно — это штатный режим ESP-IDF;
* имя вместо адреса: **mDNS** (`inkmetrics.local`) — тогда отправителю вообще не нужно знать цифры;
* адрес и способ получения показываем на экране (уже есть `net_ip_str()`/`net_mode_text()`) и на
  странице `/setup`;
* SSID и пароль — в NVS, вводятся с той же страницы `/setup` по USB (телефон и точка доступа для
  первой настройки не нужны); секреты в репозиторий не попадают.

Дополнительно от пользователя: на роутере закрепить адрес за прибором (резервирование DHCP) — тогда
адрес не «уезжает» и на него можно ссылаться в чужих настройках.

Цена: Wi-Fi-стек — это ~250 КБ флеша (место есть) и 60–80 КБ оперативной памяти в работе. PSRAM на
этой плате нет, память общая с USB и шрифтами — за этим надо следить (у нас для этого есть «чёрный
ящик» `diag`). **Оценка: один вечер.**

## Часть 2. Приём сообщений

Новый маршрут рядом с существующими:

```http
POST /notify?ttl=60&prio=1&title=Датчик
Content-Type: text/plain; charset=utf-8
X-Token: <токен>

Текст сообщения в UTF-8, до 512 байт
```

Почему именно так:

* **тело — просто текст**, без JSON: отправителю достаточно одной строки `curl`, а разбор UTF-8 в
  прошивке тривиален (у нас уже есть свой мини-разбор в `ingest.c`);
* `ttl` — сколько секунд показывать (0 — «пока не уберут», для тревог);
* `prio` — приоритет: сообщение важнее метрик, а среди сообщений побеждает старшее;
* `token` — секрет из NVS. Проверяется и в заголовке `X-Token`, и в пути `/notify/<токен>`
  (второе — для железок, которые умеют только «дёрнуть URL»). Без токена экран открыт всей семье:
  для дома это терпимо, но токен стоит копейки, поэтому он есть;
* очередь: до 8 сообщений в памяти, активное сообщение и его срок — в NVS (переживает перезагрузку).

Поведение: пока сообщение активно, панель показывает его вместо метрик, потом сама возвращается к
сводному экрану. Кнопка PWR, как и сейчас, переключает сводный ↔ SETUP; сообщение это не ломает.

Как отправлять (то, что будет в документации):

```bat
rem Windows 10/11 (PowerShell 5.1 — тело обязательно в UTF-8 байтами, иначе поедут русские буквы)
Invoke-RestMethod -Uri "http://inkmetrics.local/notify?ttl=60" -Method Post ^
  -Headers @{ "X-Token" = "<токен>" } -ContentType "text/plain; charset=utf-8" ^
  -Body ([Text.Encoding]::UTF8.GetBytes("Проверка связи"))
```

```bash
# Linux / macOS / Raspberry
curl -X POST -H 'X-Token: <токен>' -d 'Проверка связи' 'http://inkmetrics.local/notify?ttl=60'
```

```yaml
# Home Assistant (configuration.yaml)
rest_command:
  inkmetrics_say:
    url: "http://inkmetrics.local/notify?ttl=120"
    method: POST
    headers: { "X-Token": "<токен>", "Content-Type": "text/plain; charset=utf-8" }
    payload: "{{ message }}"
```

Про умный дом честно: датчик Zigbee/Z-Wave сам HTTP отправить не может — сообщение приходит через
концентратор (Home Assistant, сценарий, шлюз). Прямо «в прибор» стучатся те, кто умеет HTTP: ПК,
телефон, Raspberry, ESP. Для «родного» умного дома есть **MQTT** (в ESP-IDF есть `esp-mqtt`):
прибор подписывается на `inkmetrics/<id>/text` и показывает всё, что туда опубликовали — это
отдельная четвёртая фаза. **Оценка: один вечер.**

## Часть 3. Вывод текста и шрифты

Текст рисуем как и всё остальное: берём кегль из `fonts.h` и печатаем в кадре. Новое:

* **экран сообщения** — отдельная отрисовка (`screen_show_msg()`), врезается в ту же точку, где
  сейчас `screen_show(&st, s_page)`;
* **перенос по словам** и выравнивание (русский перенос — по пробелам, не по буквам);
* **автовыбор кегля** по длине: короткое — крупно, длинное — мелко;
* **страницы** для длинного текста (панель умеет частичную перерисовку, «мигания» не будет).

Что реально влезает в 200×200 (это и есть главное ограничение, не софт):

| Кегль | Знаков в строке | Строк | Всего на экране | Читается с |
|---|---|---|---|---|
| 12×22 | 16 | 8 | ~130 знаков | 0,7–1 м |
| 9×16 | 22 | 12 | ~260 знаков | 0,4–0,5 м |

То есть «любое сообщение» прибор покажет, но длинный текст — страницами по ~25 знаков/с. Это не
ограничение кода, а размер панели: 200×200 при 1,54" — это ~4 см по диагонали.

### Что делать со шрифтами (отдельный вопрос)

1. **Наборы.** В `tools/make_font.py` добавить набор для сообщений: латиница, кириллица заглавная и
   строчная, Ё/ё, цифры, знаки `.,:;!?-+%°()/×•–«»` — примерно 200 знаков. Сгенерировать в двух
   кеглях (9×16 и 12×22). Сам механизм уже готов: у `font_small` 168 знаков, включая 66 кириллицы —
   таблица кодпоинтов и поиск по ней есть.
2. **Подстановка вместо пропуска.** Знак, которого нет в таблице (смайлик, редкий символ), печатать
   **рамкой-заглушкой**, а не пропускать: тогда видно, что шрифт неполный, и это не выглядит как
   потеря текста. Другие письменности (арабская, китайская) не поддерживаем: растровый шрифт без
   хранения тысяч знаков их не покажет — честное ограничение, не ошибка.
3. **Лицензия.** Заодно закрывается вопрос про Consolas: генерировать из шрифта под OFL. Проверено,
   что кириллица есть и файлы доступны: **Roboto Mono, JetBrains Mono, IBM Plex Mono, Noto Sans Mono**
   (все OFL). Выбрать один и указать в `THIRD-PARTY-NOTICES.md`.
4. **Стенд.** По правилу проекта («добавил шрифт — правь и стенд») `tools/preview/` должен уметь
   новый кегль. И порядок работ как всегда: сначала **макет** сообщения и переноса, показать,
   затем прошивка.

**Оценка: один-два вечера** (шрифты + перенос + макет + заливка и проверка).

## Порядок работ и что от кого нужно

| Фаза | Что делаем | Оценка | Что нужно от пользователя |
|---|---|---|---|
| 0 | Макет: как выглядит сообщение 20/60/200 знаков, где заголовок, как листается | полвечера | посмотреть макет, сказать правки |
| 1 | Сеть: Wi-Fi + mDNS + адрес на экране и в `/setup` | вечер | подтвердить «включаем Wi-Fi», знать SSID/пароль для ввода |
| 2 | Приём: `/notify`, очередь, токен, NVS, примеры для отправки | вечер | придумать токен (или сгенерирую) |
| 3 | Вывод: экран сообщения, перенос, страницы, новые шрифты из OFL | 1–2 вечера | посмотреть макет шрифтов, подтвердить смену шрифта |
| 4 | (по желанию) MQTT-подписка для умного дома | вечер | подписаться на тему или нет |

Уровень версии после фазы 3 — минимум 0.8.0: меняются раскладка, шрифты и поведение экрана.
